# AZONE LANG Specification 0.2

## Лексика и базовый синтаксис

**Проект:** AZONE LANG
**Версия спецификации:** 0.2
**Статус:** Draft
**Исходные файлы:** .az
**Целевая реализации:** С++20
**Кодировка исходного текста:** UTF-8

### 1. Цель спецификации

Данная спецификация определяет фундаментальные правила исходного кода AZONE LANG:

- кодировку;
- структуру исходного файла;
- набор допустимых символов;
- токены;
- идентификаторы;
- ключевые слова;
- комментарии;
- литералы;
- операторы;
- разделители;
- базовые грамматические конструкции;
- правила лексического анализа.

Спецификация не определяет окончательно:

- объектную модель;
- систему типов;
- байткод;
- инструкции VM;
- механизм `.azm`;
- стандартную библиотеку.

### 2. Кодировка

Исходный код AZONE LANG должен храниться в UTF-8.

Рекомендуемая кодировка:

UTF-8

ASCII-символы используются для синтаксических конструкций языка.

Unicode разрешается использовать в:

- строковых литералах;
- символьных литералах;
- комментариях.

Использование Unicode в идентификаторах на данном этапе **не разрешается**.

Таким образом:

```AZONE
int value = 10;
string message = "Привет!";
```

разрешено.

Но:

```AZONE
int количество = 10;
```

на этапе 0.2 должно приводить к ошибке лексического анализатора.

Поддержка Unicode-идентификаторов может быть добавлена отдельной спецификацией.

### 3. Структура исходного файла

Файл `.az` состоит из последовательности элементов исходного кода:

SourceFile 
	├── Header 
	├── Imports 
	├── Declarations 
	└── EOF

Минимальный файл:

` `

пустой файл является корректным исходным файлом.

Простейшая программа:

```AZONE
print("Hello, AZONE!");
```

### 4. Регистрозависимость

AZONE LANG является регистрозависимым языком.

Следующие идентификаторы являются различными:

value
Value
VALUE
VaLuE

Аналогично:

class
Class
CLASS

являются различными последовательностями символов.

Зарезервированные ключевые слова распознаются только в нижнем регистре.

### 5. Пробельные символы

К пробельным символам относятся:

SPACE
TAB
CR
LF

 Пробельные символы между токенами обычно игнорируются.

Например:

```AZONE
int value = 10;
```

Перенос строки на этапе 0.2 не является обязательным разделителем инструкций.

Следовательно: 

```AZONE
int a = 10;
int b = 20;
```

и:

```AZONE
int a = 10; int b = 20;
```

эквивалентны.

### 6. Точка с запятой

Символ:

`;`

используется для завершения инструкций.

Пример:

```AZONE
int value = 10;
print(value);
```

В базовой версии языка автоматическая вставка `;` не используется.

Следовательно:

```AZONE
int value = 10
```

является синтаксической ошибкой.

Это решение делает синтаксис однозначным и упрощает первоначальную реализацию компилятора.

### 7. Комментарии

AZONE LANG поддерживает два вида комментариев.

#### 7.1 Однострочный комментарий

Начинается с:

`//`

Пример:

```AZONE
int value = 10; // значение пользователя
```

Все после `//` до конца строки игнорируется

#### 7.2 Многострочный комментарий

Начинается:

`/*`

и заканчивается:

`*/`

Пример:

```AZONE
/*
Это многострочный
комментарий
*/

int value = 10;
```

На этапе 0.2 вложенные многострочные комментария не поддерживаются.

### 8. Идентификаторы

Идентификатор используется для обозначения:

- переменных;
- функций;
- классов;
- методов;
- полей;
- параметров;
- модулей;
- перечислений;
- других именованных сущностей.

Формат:

Identifier ::= Letter | `"_"` followed by
Letter | Digit | `"_"`

Где:

Letter = A-Z | a-z
Digit = 0-9

Примеры корректных идентификаторов:

value
player
Player
`_player`
player1
my_variable
calculateValue

Некорректные:

123value
my-variable
hello.world
my variable

### 9. Ограничения идентификаторов

Идентификатор не может начинаться с цифры.

123abc

недопустимо.

Следующее допустимо:

abc123

Два символа подчёркивания подряд не запрещаются:

`my__value`

Также разрешается идентификатор, состоящий только из `_`, если в конкретном контексте он допускается семантическим анализатором.

### 12. Числовые литералы

Например:

### 44. Лексические категории

Лексический анализатор должен преобразовывать исходный текст в следующие категории токенов:

Identifier 
Keyword 

IntegerLiteral 
FloatLiteral 
StringLiteral 
CharLiteral 
BooleanLiteral 
NullLiteral 

Operator 
Delimiter 

Comment 
Whitespace 

EndOfFile

Комментарии и пробельные символы не передаются parser'у как обычные синтаксические токены.

### 45. Token

Внутреннее представление токена компилятора должно содержать как минимум:

Token { 
	TokenType type; 
	SourceLocation location; 
	SourceSpan span; 
	string lexeme; 
};

Где:

TokenType — тип токена 
location — позиция начала 
span — диапазон исходного текста 
lexeme — исходное текстовое представление

Конкретная реализация будет определена при разработке Lexer.

### 46. Source Location

Каждый токен должен иметь информацию о его положении:

file 
line 
column 
offset

Например:

main.az:15:8

Это необходимо для системы диагностики компилятора.

### 47. Ошибки Lexer

Лексический анализатор должен обнаруживать:

- неизвестные символы;
- незакрытые строки;
- незакрытые символьные литералы;
- незакрытые комментарии;
- неправильные числовые литералы;
- неправильные escape-последовательности;
- недопустимые идентификаторы.

Пример:

`error[L0001]: unterminated string literal`

--> main.az:4:20

### 48. Требование к Lexer

Lexer должен быть независим от Parser.

Поток:

![[Lexer req.drawio.png]]

Lexer не должен знать о значении выражений, типах или объектной модели.

Например, Lexer должен распознать:

a + b * 10

как последовательность:

IDENTIFIER 
PLUS 
IDENTIFIER 
MULTIPLY 
INTEGER

а не пытаться вычислять выражение.

### 49. Требование к Parser

Parser работает только с потоком токенов.

Он отвечает за построение AST.

Например:

a + b * 10

должно превратиться концептуально в:

![[parser req.drawio.png]]

То есть Parser должен учитывать приоритет операторов.

### 50. Формальная грамматика — предварительная версия

В дальнейшем грамматика будет записана в форме EBNF.

На текущем этапе:

program ::= declaration* EOF ; 

declaration ::= function 
			| variable 
			| class 
			| interface 
			| enum 
			| import 
			;

statement ::= variableDeclaration 
			| expressionStatement 
			| ifStatement 
			| whileStatement 
			| forStatement 
			| returnStatement 
			| breakStatement 
			| continueStatement 
			| block 
			; 

block ::= "{" statement* "}" ; 

expressionStatement ::= expression ";" ; 

variableDeclaration ::= type identifier ("=" expression)? ";" ; 

ifStatement ::= "if" "(" expression ")" statement 
			("else" statement)? ; 

whileStatement ::= "while" "(" expression ")" statement ; 

forStatement ::= "for" "(" forInitializer ";" expression? ";" expression? ")" statement ; 

returnStatement ::= "return" expression? ";" ; 

expression ::= assignment ; 

assignment ::= logicalOr (assignmentOperator assignment)? ; 

assignmentOperator ::= "=" 
					| "+=" 
					| "-=" 
					| "*=" 
					| "/=" 
					| "%=" ; 

type ::= identifier 
		| builtinType ; 

identifier ::= Identifier ;

Это **не окончательная грамматика**.

### 51. Принцип совместимости

Изменения языка должны учитывать обратную совместимость.

Каждая спецификация должна иметь версию:

[[Specification 0.1 |0.1]] 
[[Specification 0.2 |0.2 ]]
[[Specification 0.3 |0.3]] 
... 
1.0

Изменения, нарушающие существующий синтаксис, должны быть явно документированы.
