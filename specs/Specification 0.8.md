# AZONE LANG — Спецификация 0.8

## Система расширений компилятора AZM Compiler Extension System

**Версия документа:** 0.8  
**Статус:** Проектная спецификация  
**Язык реализации:** C++20  
**Целевая платформа разработки:** Linux x86-64  
**Расширение файлов:** `.azm`

---

## 1. Назначение

AZM Compiler Extension System — подсистема расширения компилятора AZONE LANG, позволяющая добавлять новые возможности языку без изменения основного исходного кода компилятора для каждого отдельного расширения.

Расширения могут предоставлять:

- новые типы данных;
- новые операторы и правила их обработки;
- дополнительные функции и встроенные функции;
- новые синтаксические конструкции и ключевые слова;
- преобразования AST;
- дополнительные этапы компиляции;
- оптимизации;
- новые атрибуты и аннотации;
- нативные функции и интеграцию с системным окружением;
- обработчики пользовательских инструкций байткода при наличии совместимой поддержки со стороны VM.

Главная задача системы — сделать AZONE LANG расширяемым языком, пригодным для создания библиотек, системных интерфейсов, инструментов разработки и компонентов будущей AZONE OS.

**Основной принцип:** расширение должно использовать публичный API компилятора и не зависеть от его внутренних деталей, если это явно не предусмотрено версией API.

## 2. Терминология

|Термин|Значение|
|---|---|
|AZC|Компилятор AZONE LANG|
|AZM|Модуль расширения компилятора|
|Manifest|Описание расширения и его требований|
|Extension API|Публичный интерфейс взаимодействия расширения с компилятором|
|Extension ABI|Бинарный контракт между расширением и средой загрузки|
|Registry|Реестр типов, операторов, функций и других элементов|
|AST|Абстрактное синтаксическое дерево|
|Compiler Pass|Этап обработки программы|
|Bytecode Extension|Расширение набора инструкций байткода|
|Native Bridge|Механизм взаимодействия VM с нативным кодом|
|Host|Процесс, загружающий расширение, например компилятор или VM|

Следует различать три вида модулей:

- `**.az**` — исходный код обычной программы или библиотеки AZONE LANG.
- `**.azb**` — скомпилированный байткод AZONE LANG.
- `**.azm**` — пакет расширения компилятора, содержащий метаданные и необходимые компоненты расширения.

Обычная библиотека `.az` не становится расширением компилятора автоматически.

## 3. Основные требования

Система расширений должна:

1. Загружать расширения без обязательной перекомпиляции самого AZC.
2. Предоставлять документированный публичный API.
3. Проверять совместимость версии расширения с компилятором.
4. Поддерживать зависимости между расширениями.
5. Обнаруживать конфликты имён и регистраций.
6. Предоставлять диагностические сообщения с указанием расширения и причины ошибки.
7. Поддерживать контролируемый порядок инициализации.
8. Позволять отключать расширения конфигурацией компилятора.
9. Обеспечивать воспроизводимость сборки при одинаковой конфигурации и входных данных.
10. Поддерживать расширения, ориентированные на hosted- и freestanding-среды.
11. Не требовать сторонних библиотек для базовой реализации.
12. Разделять API компилятора, API выполнения и внутреннюю реализацию.

## 4. Архитектура

Подсистема расширений состоит из следующих компонентов:

- **Extension Package Reader** — чтение контейнера `.azm`.
- **Manifest Parser** — чтение и проверка манифеста.
- **Extension Resolver** — поиск зависимостей и проверка совместимости.
- **Extension Loader** — загрузка нативных компонентов.
- **Extension Manager** — управление жизненным циклом.
- **Extension API** — публичные интерфейсы расширения.
- **Registration Registry** — реестры зарегистрированных элементов.
- **Compiler Hooks** — точки подключения к этапам компиляции.
- **Extension Diagnostics** — ошибки, предупреждения и журналы.
- **Compatibility Checker** — проверка версий API, ABI и возможностей компилятора.

Расширение не должно напрямую изменять внутренние структуры компилятора. Взаимодействие выполняется через предоставленные интерфейсы и реестры.

### 4.1. Общая схема

```
.azm package
    |
    v
Package Reader
    |
    v
Manifest Parser
    |
    v
Dependency Resolver
    |
    v
Compatibility Checker
    |
    v
Extension Loader
    |
    v
Extension Initialize()
    |
    v
Registration Registry
    |
    v
Compiler Pipeline
    |
    v
.azb output
```

Если расширение использует собственные инструкции байткода, дополнительно требуется совместимая реализация этих инструкций на стороне виртуальной машины.

## 5. Формат пакета `.azm`

`.azm` определяется как контейнер расширения, а не просто произвольная динамическая библиотека с изменённым расширением файла.

Пакет может включать:

- манифест;
- нативную библиотеку расширения;
- вспомогательные метаданные;
- дополнительные ресурсы;
- описание требований к VM;
- описание поддерживаемых платформ;
- данные для диагностики и документацию.

### 5.1. Логическая структура

```
example.azm
├── manifest
├── native/
│   └── extension.so
├── metadata/
│   └── types
└── resources/
```

Это логическое представление, а не требование к конкретной файловой системе контейнера.

В первой реализации допустимо использовать простой пакет с манифестом и отдельной нативной библиотекой. В дальнейшем можно определить единый бинарный формат контейнера с заголовком, версией формата, таблицей файлов, смещениями и контрольными суммами.

### 5.2. Манифест

Манифест должен содержать как минимум:

- уникальный идентификатор расширения;
- отображаемое имя;
- версию расширения;
- версию Extension API;
- требуемую версию компилятора;
- целевые платформы;
- точку входа расширения;
- список зависимостей;
- предоставляемые возможности;
- сведения о наличии нативного кода;
- требования к VM, если они есть.

Пример условного манифеста:

```
extension: "azone.math"
name: "AZONE Math Extensions"
version: "1.0.0"
api: "1"
compiler: ">=0.8.0 <1.0.0"
platforms: ["linux-x86_64"]
entry: "azone_math_extension_init"
capabilities: ["types", "operators", "functions"]
dependencies: []
```

Приведённая запись иллюстрирует содержание манифеста. Конкретная грамматика, правила экранирования, кодировка и формат сериализации определяются реализационной спецификацией формата `.azm`.

Манифест не должен считаться доказательством безопасности расширения: указанные в нём возможности являются декларацией, которую загрузчик проверяет в соответствии с политикой среды.

## 6. Идентификаторы, версии и совместимость

### 6.1. Идентификатор расширения

Каждое расширение должно иметь уникальный идентификатор, например:

```
azone.math
azone.network
azone.compiler.optimizations
community.json
```

Идентификатор используется для разрешения зависимостей, диагностики и предотвращения конфликтов.

### 6.2. Версионирование

Версия расширения должна отличаться от версии Extension API и версии компилятора.

- **Версия расширения** описывает развитие конкретного модуля.
- **Версия API** описывает доступные интерфейсы расширения.
- **Версия компилятора** описывает конкретную реализацию AZC.
- **Версия байткода** описывает совместимость генерируемого `.azb`.
- **Версия VM API** описывает интерфейсы расширений, работающих во время выполнения.

Совместимость должна проверяться по явно заданным ограничениям, а не по совпадению номеров версий.

Изменения, несовместимые с предыдущим ABI, требуют отдельной версии ABI либо механизма адаптации.

## 7. Публичный Extension API

Расширение должно получать доступ к функциям компилятора через объект контекста, предоставленный загрузчиком.

Концептуальный интерфейс:

```c++
struct ExtensionContext {
    CompilerAPI* compiler;
    TypeRegistry* types;
    OperatorRegistry* operators;
    FunctionRegistry* functions;
    SyntaxRegistry* syntax;
    PassRegistry* passes;
    DiagnosticAPI* diagnostics;
};

class CompilerExtension {
public:
    virtual ~CompilerExtension() = default;

    virtual bool initialize(
        ExtensionContext& context
    ) = 0;

    virtual void shutdown() = 0;
};
```

Это пример архитектурного интерфейса на C++20, а не окончательный бинарный ABI. Непосредственное использование C++-виртуальных классов между независимо собранными динамическими модулями требует согласованных компилятора, стандартной библиотеки, ABI и настроек сборки.

### 7.1. Требования к API

Публичный API должен:

- предоставлять только документированные операции;
- проверять корректность аргументов;
- передавать ошибки через определённый механизм;
- предоставлять доступ к диагностике;
- поддерживать регистрацию и отмену регистрации элементов;
- определять владение памятью;
- определять правила работы с потоками;
- определять срок жизни объектов API;
- не передавать исключения C++ через границу ABI;
- не требовать от расширения знания внутренних адресов и структур компилятора.

### 7.2. Стабильная граница ABI

Для первой стабильной версии рекомендуется использовать **C-совместимую ABI-границу** с версионированными таблицами функций, непрозрачными указателями и типами фиксированного размера.

C++20 применяется для реализации самого компилятора и расширений, но внутренние C++-классы не должны автоматически считаться стабильным межмодульным ABI.

Пример концептуальной точки входа:

```c++
extern "C"
ExtensionStatus azone_extension_init(
    const ExtensionHostAPI* host,
    ExtensionAPI* extension
);
```

Точный набор структур и функций будет определён в заголовках публичного SDK. Все структуры, пересекающие границу ABI, должны иметь однозначно определённые правила размера, выравнивания, владения памятью и версионирования.

## 8. Регистрация возможностей

Каждое расширение может регистрировать только те категории возможностей, которые поддерживаются его API и разрешены конфигурацией компилятора.

Основные реестры:

|Реестр|Назначение|
|---|---|
|Type Registry|Новые типы и метаданные типов|
|Operator Registry|Операторы и их семантика|
|Function Registry|Функции и встроенные функции|
|Syntax Registry|Ключевые слова и синтаксические формы|
|AST Registry|Дополнительные узлы AST и их обработчики|
|Pass Registry|Этапы обработки и оптимизации|
|Attribute Registry|Атрибуты и аннотации|
|Bytecode Registry|Описания расширенных инструкций|
|Runtime Registry|Компоненты, необходимые во время выполнения|
|Native Function Registry|Нативные функции и их сигнатуры|

Регистрация должна выполняться явно, через API. Простое наличие символа в динамической библиотеке не должно автоматически добавлять новую возможность языку.

### 8.1. Конфликты

Система обязана обнаруживать:

- повторную регистрацию идентификатора;
- несовместимые сигнатуры;
- конфликтующие определения операторов;
- дублирующиеся ключевые слова;
- повторные идентификаторы инструкций;
- циклические зависимости;
- конфликтующие требования к версиям.

По умолчанию конфликт должен приводить к ошибке загрузки или компиляции. Неявная замена ранее зарегистрированной возможности запрещена.

Если переопределение разрешено отдельным механизмом, оно должно быть явно запрошено и отображаться в диагностике.

## 9. Расширение системы типов

Расширение может объявлять новые типы, если они поддерживаются системой типов AZONE LANG.

Для каждого типа могут определяться:

- уникальный идентификатор;
- имя;
- категория типа;
- размер и выравнивание, если применимо;
- правила создания значений;
- правила копирования и присваивания;
- правила сравнения;
- допустимые преобразования;
- поддерживаемые операторы;
- информация для диагностики;
- требования к управлению памятью;
- правила взаимодействия с VM и нативным ABI.

Расширение не должно произвольно изменять фундаментальные свойства уже существующих типов.

### 9.1. Пример

Условный модуль может предоставлять тип `vector3` с арифметическими операциями.

```
vector3 a = vector3(1.0, 2.0, 3.0);
vector3 b = vector3(4.0, 5.0, 6.0);

vector3 c = a + b;
```

Компилятор должен проверить существование типа, допустимость вызова конструктора и наличие подходящей реализации оператора `+`.

Пример показывает предполагаемую возможность языка; окончательная форма объявления расширенных типов определяется спецификацией синтаксиса расширений.

## 10. Расширение операторов

Расширение может регистрировать операторы для новых типов, если соблюдаются правила грамматики и семантики языка.

Описание оператора должно включать:

- символ или идентификатор оператора;
- число операндов;
- поддерживаемые типы;
- тип результата;
- приоритет и ассоциативность, если оператор участвует в синтаксисе выражений;
- правила проверки типов;
- способ генерации кода;
- дополнительные ограничения безопасности.

### 10.1. Приоритеты

Добавление нового оператора не должно незаметно менять разбор существующих программ.

В MVP рекомендуется разрешить расширениям регистрировать семантику уже предусмотренных операторных форм. Введение новых символов и изменение таблицы приоритетов следует разрешать только через отдельные декларации грамматики с обязательной проверкой конфликтов.

Если новое правило делает грамматику неоднозначной, компилятор должен отклонить регистрацию либо потребовать явного разрешения неоднозначности в соответствии с правилами языка.

## 11. Расширение функций

Расширения могут предоставлять встроенные функции, функции компилятора и декларации нативных функций.

Для каждой функции должны определяться:

- уникальное имя;
- сигнатура;
- тип результата;
- параметры;
- соглашение о вызовах;
- требования к памяти и владению ресурсами;
- возможные побочные эффекты;
- доступность в hosted- и freestanding-режимах;
- механизм реализации.

Встроенная функция может преобразовываться компилятором в последовательность байткода без обычного вызова функции, если это предусмотрено её описанием.

Функции, выполняемые во время исполнения, должны иметь соответствующую реализацию в VM или Native Bridge.

Нельзя считать, что регистрация функции в компиляторе автоматически делает её доступной виртуальной машине.

## 12. Расширение синтаксиса и AST

Расширение может добавлять синтаксические конструкции через официальные точки подключения парсера.

Возможные механизмы:

- регистрация ключевых слов;
- регистрация атрибутов;
- объявление новых синтаксических форм;
- создание дополнительных типов узлов AST;
- обработчики разбора;
- преобразование расширенного синтаксиса в стандартный AST.

### 12.1. Рекомендация для MVP

На первом этапе предпочтительно использовать **преобразование расширенного синтаксиса в существующие конструкции языка**.

Например, специальная конструкция может преобразовываться в обычный вызов функции или стандартный узел AST. Это уменьшает зависимость расширения от внутренних механизмов компилятора.

Если расширение создаёт собственные узлы AST, оно обязано предоставить необходимые операции проверки, обхода и преобразования. Все последующие этапы компилятора должны корректно обрабатывать такие узлы либо получать уже преобразованное стандартное AST.

### 12.2. Ключевые слова

Ключевые слова ядра языка имеют приоритет над пользовательскими расширениями.

Расширение не может без специального механизма переопределить `class`, `return`, `if`, `while`, `module`, `import` или другие зарезервированные слова.

Для пользовательских конструкций предпочтительно использовать пространства имён, атрибуты и явно подключаемые синтаксические модули.

## 13. Этапы компиляции

Расширения могут добавлять этапы компиляции через Pass Registry.

Этап может выполняться на одном из согласованных уровней:

1. После построения AST.
2. После семантической проверки.
3. После разрешения типов.
4. Перед генерацией байткода.
5. После генерации промежуточного представления.
6. На этапе оптимизации, если такой этап поддерживается.

Для каждого этапа должны быть определены входные данные, выходные данные, допустимые изменения и зависимости от других этапов.

### 13.1. Порядок выполнения

Компилятор должен строить порядок этапов с учётом объявленных зависимостей.

Если порядок однозначно определить невозможно из-за циклических зависимостей, компиляция должна завершиться диагностируемой ошибкой.

При одинаковой конфигурации расширений порядок этапов должен быть воспроизводимым.

### 13.2. Ошибки этапов

Если этап возвращает ошибку, компилятор должен:

- зафиксировать диагностику;
- прекратить выполнение зависимых этапов;
- освободить принадлежащие этапу временные ресурсы;
- не выдавать итоговый `.azb` как успешно скомпилированный файл.

Компилятор не должен продолжать обработку некорректного состояния AST или промежуточного представления без явно определённого механизма восстановления.

## 14. Расширение байткода

Система расширений может описывать пользовательские инструкции байткода, но сама регистрация инструкции не гарантирует, что VM сможет её выполнить.

Каждая инструкция должна иметь определённые:

- уникальный идентификатор;
- версию;
- формат операндов;
- требования к стеку;
- влияние на состояние VM;
- правила проверки типов;
- правила управления памятью;
- обработку ошибок;
- реализацию или механизм понижения до стандартных инструкций.

### 14.1. Рекомендуемый порядок реализации

**Первый уровень — понижение в стандартный байткод.**

Расширение реализует высокоуровневую конструкцию, а компилятор преобразует её в уже существующие инструкции `.azb`. Это предпочтительный механизм для MVP.

**Второй уровень — расширения VM.**

Для пользовательских инструкций VM требуется совместимый обработчик и механизм регистрации, проверки и диспетчеризации. Файл `.azb` должен явно указывать требования к расширениям и версиям, необходимым для исполнения.

Неизвестная обязательная инструкция не должна молча пропускаться или интерпретироваться как другая операция.

### 14.2. Совместимость `.azb`

Байткод, использующий расширенные инструкции, должен содержать информацию о необходимых расширениях и версиях их контрактов.

VM должна до начала выполнения проверить, доступны ли необходимые обработчики.

Если необходимое расширение отсутствует или несовместимо, загрузка программы должна завершиться ошибкой совместимости.

## 15. Интеграция с VM и Native Bridge

Расширение компилятора может объявить нативную функцию, однако её выполнение требует доступной реализации и зарегистрированной сигнатуры в соответствующей среде исполнения.

Путь вызова может выглядеть следующим образом:

```
AZONE LANG source
       |
       v
Compiler Extension
       |
       v
Native Function Declaration
       |
       v
.azb function call
       |
       v
VM Native Bridge
       |
       v
Native Implementation
```

Для нативных вызовов должны быть определены:

- типы параметров и результата;
- соглашение о вызовах;
- правила владения памятью;
- поведение при ошибках;
- доступность в текущем режиме выполнения;
- требования к безопасности и правам доступа.

Расширение компилятора не должно автоматически получать право выполнять произвольные нативные функции в целевой программе.

## 16. Загрузка и жизненный цикл

Жизненный цикл расширения включает следующие состояния:

1. **Discovered** — пакет найден.
2. **Parsed** — манифест прочитан.
3. **Validated** — структура и требования проверены.
4. **Resolved** — зависимости найдены.
5. **Loaded** — нативный компонент загружен.
6. **Initialized** — расширение успешно инициализировано.
7. **Active** — расширение участвует в работе компилятора.
8. **Shutting Down** — выполняется завершение работы.
9. **Unloaded** — нативный компонент выгружен, если это безопасно.
10. **Failed** — загрузка или инициализация завершилась ошибкой.

Переходы между состояниями должны контролироваться Extension Manager.

### 16.1. Инициализация

Во время инициализации расширение получает Extension API и регистрирует свои возможности.

Если инициализация завершается неудачно, все регистрации, выполненные этим расширением, должны быть отменены, если они ещё не стали частью активной компиляции или другого объекта с более длительным сроком жизни.

Инициализация не должна приводить к частично активному состоянию, при котором часть расширения зарегистрирована, а часть отсутствует.

### 16.2. Завершение и выгрузка

Нативный код нельзя безопасно выгружать, если на его функции, таблицы виртуальных методов, обработчики, объекты или данные всё ещё существуют ссылки.

Поэтому в первой версии рекомендуется:

- разрешать отключение расширения перед началом новой компиляции;
- запрещать выгрузку расширения, используемого активной компиляцией;
- выгружать библиотеку только после завершения всех вызовов и освобождения принадлежащих ей объектов;
- в сложных случаях оставлять библиотеку загруженной до завершения процесса AZC.

**Возможность отключить расширение и возможность физически выгрузить его нативную библиотеку — разные операции.**

## 17. Зависимости между расширениями

Расширения могут объявлять зависимости от других расширений.

Для каждой зависимости указываются:

- идентификатор;
- допустимый диапазон версий;
- обязательность зависимости;
- необходимые возможности, если применимо.

Загрузчик должен:

1. Найти все обязательные зависимости.
2. Проверить версии и совместимость.
3. Построить граф зависимостей.
4. Определить порядок инициализации.
5. Обнаружить циклы.
6. Инициализировать расширения в согласованном порядке.

При отсутствии обязательной зависимости расширение не должно активироваться.

В MVP циклические зависимости расширений запрещены. В дальнейшем можно рассмотреть ограниченную модель взаимных зависимостей с отдельной фазой объявления интерфейсов, но она не является требованием первой реализации.

## 18. Безопасность

Нативное расширение `.azm`, загруженное в процесс компилятора, фактически получает полномочия этого процесса.

Оно потенциально может обращаться к памяти компилятора, файловой системе, системным вызовам и другим ресурсам, доступным процессу.

Следовательно, `**.azm**` **с нативным кодом нельзя считать безопасным или изолированным модулем только из-за наличия манифеста либо специального расширения файла**.

### 18.1. Базовые требования

Система должна:

- поддерживать явное разрешение загрузки расширений;
- позволять отключать загрузку расширений;
- проверять структуру пакета до загрузки нативного кода;
- проверять версии API и ABI;
- ограничивать доступные операции через публичный API;
- выводить предупреждение при загрузке неизвестного нативного расширения;
- поддерживать проверку хешей пакетов;
- в будущем предусматривать цифровые подписи и политику доверенных издателей.

Проверка хеша подтверждает целостность относительно известного значения, но сама по себе не подтверждает безопасность автора или кода.

### 18.2. Доверие

В системе должны различаться:

- доверенные системные расширения;
- локальные расширения разработчика;
- сторонние расширения;
- расширения, запрещённые политикой среды.

Политика доверия определяется конфигурацией запуска компилятора или системного окружения.

Нативный код расширения не должен загружаться из недоверенных источников автоматически.

### 18.3. Будущая изоляция

В дальнейшем может быть добавлен отдельный формат расширений без произвольного нативного кода — например, декларативные расширения или модули с ограниченной моделью исполнения.

Такой формат позволит ограничивать возможности расширения сильнее, чем нативная библиотека. Однако он не входит в обязательный объём MVP.

## 19. Hosted и Freestanding режимы

AZONE LANG предназначен не только для обычных приложений, но и для будущей AZONE OS.

Поэтому система расширений должна различать окружения:

- **Hosted** — компилятор работает в обычной операционной системе и может использовать её средства загрузки динамических библиотек.
- **Freestanding** — доступные системные функции могут быть ограничены; стандартный механизм загрузки динамических библиотек может отсутствовать.

В hosted-реализации Linux для загрузки нативных расширений можно использовать системный механизм динамических библиотек, например `dlopen`/`dlsym`, без стороннего фреймворка.

При этом интерфейс Extension Loader должен быть абстрагирован от конкретного механизма загрузки.

В freestanding-среде загрузка нативных расширений может быть отключена либо предоставляться специализированным загрузчиком. Нельзя предполагать наличие файловой системы, динамического линкера или полноценной стандартной библиотеки C++.

Компилятор, работающий на Linux, и программы AZONE LANG, исполняемые будущей AZONE OS, — разные среды. Возможность загрузить `.azm` в компилятор не означает автоматическую возможность загрузить тот же модуль в целевую операционную систему.

## 20. Диагностика

Ошибки расширений должны содержать:

- идентификатор и версию расширения;
- стадию, на которой возникла ошибка;
- категорию ошибки;
- понятное описание;
- имя конфликтующего элемента, если применимо;
- рекомендации по исправлению, если их можно определить.

Основные категории ошибок:

- ошибка структуры пакета;
- ошибка манифеста;
- несовместимая версия API или ABI;
- отсутствующая зависимость;
- циклическая зависимость;
- конфликт регистрации;
- ошибка инициализации;
- ошибка Compiler Pass;
- отсутствующая реализация инструкции VM;
- несовместимость `.azb`;
- ошибка нативного вызова;
- нарушение политики доверия.

Сбой расширения не должен маскироваться под успешную компиляцию.

## 21. Конфигурация компилятора

AZC должен поддерживать конфигурацию загрузки расширений.

Предусматриваемые возможности:

- включение и отключение системы расширений;
- указание каталогов поиска;
- явное подключение расширений;
- отключение отдельных модулей;
- проверка зависимостей без полноценной компиляции;
- вывод списка загруженных расширений;
- вывод информации о совместимости;
- режим диагностики загрузки;
- ограничение разрешённых возможностей.

Конкретные параметры CLI будут определены спецификацией интерфейса командной строки.

Компилятор должен обеспечивать возможность сборки без сторонних расширений, чтобы ядро языка оставалось работоспособным независимо от установленных модулей.

## 22. Воспроизводимость сборки

Чтобы результаты компиляции не зависели от случайного порядка загрузки расширений, система должна обеспечивать:

- детерминированный порядок инициализации;
- детерминированный порядок Compiler Pass;
- стабильные правила разрешения имён;
- явную фиксацию версий расширений;
- явную фиксацию требований к VM и байткоду;
- документированные источники недетерминизма.

Если расширение использует время, случайные числа, внешние файлы или системное окружение при генерации кода, такие зависимости должны быть либо запрещены в воспроизводимом режиме, либо явно объявлены и контролироваться сборочной системой.

## 23. Тестирование расширений

Каждое расширение должно иметь возможность проходить следующие проверки:

1. Проверка корректности манифеста.
2. Проверка совместимости API и ABI.
3. Проверка зависимостей.
4. Проверка регистрации возможностей.
5. Проверка обнаружения конфликтов.
6. Проверка диагностики ошибок.
7. Проверка преобразований AST.
8. Проверка порядка Compiler Pass.
9. Проверка корректности генерируемого байткода.
10. Проверка совместимости с VM, если она требуется.
11. Проверка завершения работы и освобождения ресурсов.
12. Проверка поведения при ошибке инициализации.

Для системных расширений следует дополнительно проверять работу в hosted- и freestanding-конфигурациях, если расширение заявляет поддержку обеих сред.

## 24. План реализации

### Этап 1 — минимальный загрузчик

- Определить формат манифеста.
- Реализовать проверку идентификаторов и версий.
- Реализовать Extension Manager.
- Добавить механизм загрузки нативной библиотеки в Linux.
- Реализовать точку входа расширения.
- Добавить регистрацию функций.
- Реализовать базовую диагностику.
- Обеспечить отключение расширений.

### Этап 2 — расширение возможностей компилятора

- Добавить Type Registry.
- Добавить Operator Registry.
- Добавить Attribute Registry.
- Реализовать регистрацию Compiler Pass.
- Добавить проверки конфликтов.
- Реализовать граф зависимостей.
- Определить правила отмены регистраций.

### Этап 3 — расширение синтаксиса

- Добавить API для синтаксических обработчиков.
- Определить правила расширения AST.
- Реализовать преобразование пользовательских конструкций в стандартное AST.
- Добавить проверки совместимости с последующими этапами компилятора.

### Этап 4 — интеграция с VM

- Определить контракт Native Bridge.
- Реализовать регистрацию нативных функций.
- Добавить проверку требований `.azb`.
- Определить API для пользовательских инструкций, если он понадобится.
- Обеспечить диагностику отсутствующих обработчиков.

### Этап 5 — безопасность и зрелость

- Реализовать политики доверия.
- Добавить проверку целостности пакетов.
- Разработать механизм цифровых подписей.
- Улучшить воспроизводимость сборки.
- Определить поддержку freestanding-загрузчика расширений.
- Зафиксировать стабильную версию Extension API и ABI.

## 25. Ограничения MVP

Первая версия AZM Compiler Extension System должна поддерживать:

- чтение манифеста;
- проверку совместимости;
- загрузку нативного модуля в hosted-среде Linux;
- регистрацию функций и типов;
- базовые диагностические сообщения;
- зависимости расширений;
- контролируемую инициализацию и завершение;
- отключение расширений;
- генерацию стандартного байткода существующими средствами компилятора.

Следующие возможности не являются обязательными для MVP:

- произвольные новые инструкции VM;
- безопасная горячая выгрузка нативного кода;
- динамическая замена уже активных Compiler Pass;
- полностью независимый от платформы нативный ABI;
- безопасная изоляция недоверенных нативных расширений;
- полноценный freestanding-загрузчик;
- автоматическая установка расширений из сетевых репозиториев.

## 26. Критерии готовности

Спецификация считается реализованной на уровне MVP, если:

- компилятор обнаруживает и проверяет `.azm`;
- несовместимые расширения отклоняются до начала компиляции;
- расширение может зарегистрировать функцию и тип через публичный API;
- зарегистрированные возможности корректно участвуют в проверке программы и генерации кода;
- конфликты регистраций обнаруживаются;
- зависимости загружаются в детерминированном порядке;
- ошибки инициализации не оставляют частично активных регистраций;
- расширения можно отключить без пересборки компилятора;
- компиляция без расширений продолжает работать;
- требования к VM и байткоду проверяются до исполнения;
- нативные расширения не считаются автоматически безопасными или изолированными.
