# AZONE LANG Specification 0.1
## Техническое задание на разработку языка программирования

**Кодовое название**: AZONE LANG
**Расширение исходных файлов**: .az
**Расширение файлов расширений компилятора**: .azm
**Тип языка**: компилируемый
**Модель выполнения**: виртуальная машина
**Архитектура VM**: стековая
**Парадигма**: объектно-ориентированная
**Система типов**: статическая
**Язык реализации**: C++20
**Платформа разработки**: Arch Linux
**Сторонние библиотеки**: не используются
**Фреймворки**: не используются

### 1. Назначение проекта

AZONE LANG - самостоятельно разрабатываемый компилируемый объектно-ориентированный язык программирования с собственной виртуальной машиной, компилятором, системой типов, форматом байткода и механизмом расширения возможностей компилятора.

Основная цель проекта - создать самостоятельную программную платформу, позволяющую: 

- разрабатывать прикладные программы;
- создавать объектно-ориентированные приложения;
- работать с памятью и аппаратными ресурсами на низком уровне;
- расширять возможности языка и компилятора;
- добавлять новые типы данных;
- добавлять новые операторы;
- интегрировать С/С++-код;
- встраивать виртуальную машину в другие приложения;
- использовать язык как самостоятельный инструмент либо как встроенный скриптовый/программный движок.

### 2. Основные принципы

AZONE LANG должен разрабатываться как самостоятельная система.

Не допускается зависимость основных компонентов от сторонних компиляторов, виртуальных машин, парсеров или LLVM-подобных инфраструктур.

Все ключевые компоненты реализуются самостоятельно на С++20:

1. лексический анализатор;
2. синтаксический анализатор;
3. AST;
4. система типов;
5. семантический анализатор;
6. компилятор;
7. формат байткода;
8. виртуальная машина;
9. объектная система;
10. система управления памятью;
11. механизм расширений;
12. runtime;
13. API встраивания VM.

Стандартная библиотека С++ может использоваться для базовых задач реализации.

### 4. Исходные файлы

`.az`

Файл `.az` содержит исходный код программы или модуля AZONE LANG

### 5. Файлы расширений компилятора

Расширение:

`.azm`

.azm предназначен для системы расширений AZONE LANG.

Расширения должны позволять модифицировать возможности компилятора без изменения исходного кода самого компилятора.

Потенциальные возможности .azm:

- добавление новых типов;
- добавление операторов;
- добавление встроенных функций;
- добавление атрибутов;
- добавление новых конструкций языка;
- изменение/расширение семантического анализа;
- добавление генераторов байткода;
- регистрация runtime-функций;
- регистрация native-функций;
- взаимодействие с аппаратным обеспечением.

Конкретная архитектура .azm должна быть определена отдельным разделом спецификации после создания базового компилятора.

### 7. Байткод

Компилятор не должен непосредственно выполнять исходный код.

Исходный код преобразуется в промежуточное представление — байткод AZONE VM.

Предлагаемое расширение скомпилированного файла:

>.azb

Формат `.azb` должен содержать как минимум:

Header 
Version 
Flags 
Constant 
Pool 
Type Table 
String Table 
Function Table 
Class Table 
Method Table 
Global Data 
Bytecode 
Debug Information

Формат должен иметь версию.

Например:

AZBC 
Version: 1

Это позволит в будущем менять формат байткода без полной несовместимости со старыми версиями.

AZONE LANG использует статическую типизацию.

Тип выражения должен быть известен компилятору до запуска программы, за исключением специально предусмотренных динамических механизмов.

Базовые типы должны включать:

void 
bool 

int8 
int16 
int32 
int64 

uint8 
uint16 
uint32 
uint64 
float32 
float64 

char 
string

Также предусматриваются:

class 
interface 
array 
function 
pointer 
reference 
enum

Точный набор базовых типов будет утверждён отдельной спецификацией системы типов.

### 9. Объектно-ориентированная модель

AZONE LANG должен поддерживать объектно-ориентированное программирование.

Минимальная модель должна включать:

- классы;
- объекты;
- поля;
- методы;
- конструкторы;
- деструкторы/финализаторы при необходимости;
- наследование;
- полиморфизм;
- виртуальные методы;
- интерфейсы;
- модификаторы доступа;
- статические поля;
- статические методы;
- свойства/аксессоры при необходимости.

Пример концептуальной модели:

Animal
	│ 
	├── Dog 
	│ 
	└── Dragon

### 10. Расширяемость языка

Расширяемость является одним из фундаментальных требований AZONE LANG.

Архитектура должна позволять добавлять возможности без переписывания ядра компилятора.

Необходимо предусмотреть API регистрации:

Type Registry 
Operator Registry 
Function Registry 
Keyword Registry 
AST Extension Registry 
Compiler Pass Registry 
Bytecode Registry 
Runtime Registry 
Native Function Registry

Концептуально:

compiler.registerType(...); 
compiler.registerOperator(...); compiler.registerFunction(...); compiler.registerKeyword(...);

Конкретный C++ API будет разработан после определения внутренней архитектуры компилятора.

### 11. Расширяемые типы

Система расширений должна позволять создавать новые типы.

Например, модуль может предоставить:

Vector2 
Vector3 
Matrix4 
Socket 
File 
Device 
GPUBuffer

Новый тип должен иметь возможность взаимодействовать с:

- системой типов;
- компилятором;
- VM;
- runtime;
- сборщиком/менеджером памяти;
- операторами;
- методами.

### 12. Расширяемые операторы

Компилятор должен иметь механизм регистрации операторов.

Например:
>+ 
>- 
>* 
> / 
> == 
> != 
> <
> '>'
> <= 
> '>='

В будущем расширение может добавлять собственные операторы.

Например:

a <=> b

или пользовательские операторы, если это будет разрешено синтаксисом языка.

При этом оператор должен быть связан с определёнными типами и правилами семантической проверки.

### 13. Низкоуровневый доступ

AZONE LANG должен предоставлять контролируемый низкоуровневый доступ.

Необходимо предусмотреть:

- указатели;
- ссылки;
- адресную арифметику;
- работу с блоками памяти;
- ручное выделение памяти для специальных случаев;
- доступ к memory-mapped ресурсам;
- вызов native-функций;
- взаимодействие с C/C++;
- возможность работы с аппаратными интерфейсами ОС.

Пример концепции:

`pointer<T>`
`reference<T>` 
address memory.read(...) 
memory.write(...)

Конкретный синтаксис пока не фиксируется.

Низкоуровневые возможности должны быть отделены от безопасной части языка.

### 15. Встраиваемость

Виртуальная машина должна проектироваться как отдельный C++-компонент.

Внешняя программа должна иметь возможность концептуально выполнить:

```AZONE
AzoneVM vm;

vm.load("program.azb"); vm.run();
```

Также предусматривается возможность:

```AZONE
vm.registerNativeFunction(...); 
vm.registerType(...); 
vm.setGlobal(...); 
vm.call(...);
```

Таким образом, AZONE LANG сможет использоваться не только как самостоятельный язык, но и как embedded runtime.

### 16. Runtime

Runtime является связующим слоем между байткодом, VM и внешним окружением.

Основные компоненты:

Memory Manager 
Object Manager 
Type System 
String System 
Array System 
Exception System 
Native API 
IO 
Threading 
Reflection

Некоторые компоненты могут быть реализованы постепенно.

### 17. Управление памятью

Система управления памятью должна учитывать объектную модель языка.

Первоначально допускается реализация простой управляемой кучи.

В дальнейшем рекомендуется реализовать собственный Garbage Collector.

Предварительная архитектура:

![[Memory architecture.drawio.png]]

Тип GC будет определён после появления базовой объектной системы.

### 18. Компилятор

Компилятор AZONE LANG должен состоять из независимых стадий:

![[Compiler.drawio.png]]

Использование IR желательно предусмотреть сразу, даже если первая версия компилятора сможет генерировать байткод непосредственно из AST.

IR даст возможность впоследствии реализовать оптимизации.

### 19. Диагностика ошибок

Компилятор должен выдавать структурированные сообщения об ошибках.

Пример:

> error[E1024]: incompatible types
> 
>    --> main.az:12:15
>    
>   12 | int value = "Hello";
>	|                    ^^^^^^
>expected: int
>found:       string

Диагностика должна содержать:

- тип ошибки;
- код ошибки;
- файл;
- строку;
- столбец;
- описание;
- фрагмент исходного кода;
- указатель на проблемное место;
- дополнительную информацию при необходимости.

### 22. Этапы разработки

#### Этап 0 — спецификация

Разработать:

- синтаксис;
- лексические правила;
- типы;
- объектную модель;
- байткод;
- архитектуру VM;
- систему модулей;
- систему расширений.

#### Этап 1 — Lexer

Реализовать:

- идентификаторы;
- ключевые слова;
- числа;
- строки;
- символы;
- операторы;
- комментарии;
- позиции исходного кода.

#### Этап 2 — Parser

Создать AST и поддержать базовый синтаксис.

#### Этап 3 — Semantic Analyzer

Реализовать:

- области видимости;
- разрешение имён;
- типизацию;
- проверку выражений;
- проверку функций.

#### Этап 4 — Bytecode

Создать спецификацию инструкций и `.azb`.

#### Этап 5 — VM

Реализовать стековую VM.

#### Этап 6 — Objects

Добавить классы и объекты.

#### Этап 7 — Runtime

Создать базовый runtime.

#### Этап 8 — Extensions

Реализовать `.azm` и API расширений.

#### Этап 9 — Native API

Добавить взаимодействие с C/C++.

#### Этап 10 — Embedded VM

Сделать VM библиотекой, которую можно встраивать в другие программы.

### 24. Принцип разработки

Разработка должна идти от простого к сложному.

Каждый крупный компонент должен иметь самостоятельные тесты.

Новая возможность не должна нарушать уже реализованный функционал.

Спецификация языка должна версионироваться отдельно от реализации компилятора.
