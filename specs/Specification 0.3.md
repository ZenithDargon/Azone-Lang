# AZONE LANG Specification 0.3

## Система типов и модель выражений

**Проект:** AZONE LANG  
**Версия спецификации:** 0.3  
**Статус:** Draft  
**Целевая платформа:** собственная операционная система на базе Linux kernel  
**Назначение:** системный и прикладной язык программирования  
**Типизация:** статическая  
**VM:** стековая  
**Реализация компилятора:** C++20

---
# 1. Назначение

AZONE LANG должен использоваться как основной язык программирования для собственной операционной системы, базирующейся на Linux kernel.

В перспективе на AZONE LANG должны разрабатываться:

- системные службы;
- пользовательские процессы;
- системные утилиты;
- приложения;
- графические приложения;
- экранный сервер;
- элементы пользовательского окружения;
- системные API;
- драйверные и аппаратные интерфейсы, где это возможно;
- runtime-компоненты;
- инструменты разработки.

Поэтому система типов должна одновременно обеспечивать:

1. безопасность и удобство высокоуровневого программирования;
2. предсказуемое представление данных в памяти;
3. возможность низкоуровневого программирования;
4. прямую работу с адресами;
5. взаимодействие с ABI;
6. взаимодействие с C/C++ и native-кодом;
7. возможность работы в окружениях с ограниченным runtime.

---
# 2. Уровни выполнения AZONE LANG

AZONE LANG должен предусматривать несколько уровней выполнения.

```
┌─────────────────────────────────────────┐
│              AZONE Applications         │
├─────────────────────────────────────────┤
│           AZONE System Services         │
├─────────────────────────────────────────┤
│          AZONE Runtime / VM             │
├─────────────────────────────────────────┤
│         Native / Hardware API           │
├─────────────────────────────────────────┤
│              Linux Kernel               │
├─────────────────────────────────────────┤
│                Hardware                 │
└─────────────────────────────────────────┘
```

При этом VM не должна быть единственным способом выполнения AZONE-кода.

В дальнейшем архитектура должна допускать несколько backend'ов:

```
AZONE Source
     │
     ▼
   AST / IR
     │
 ┌───┴───────────────┐
 │                   │
 ▼                   ▼
AZONE VM          Native Backend
 │                   │
 ▼                   ▼
Runtime          CPU Machine Code
```

Первоначальная реализация будет ориентирована на VM.

# 3. Общая система типов

AZONE LANG использует статическую типизацию.

Каждое выражение должно иметь известный тип на этапе компиляции.

Основные категории:

```
Primitive Types
Reference Types
Pointer Types
Function Types
User Types
Special Types
```

---
# 4. Примитивные целочисленные типы

AZONE LANG предоставляет целочисленные типы с фиксированным размером.

```
int8
int16
int32
int64

uint8
uint16
uint32
uint64
```

Размер определяется строго:

```
int8    = 8 bits
int16   = 16 bits
int32   = 32 bits
int64   = 64 bits

uint8   = 8 bits
uint16  = 16 bits
uint32  = 32 bits
uint64  = 64 bits
```

Размер не зависит от платформы.

Это особенно важно для системного программирования.

---
# 5. Типы размерности платформы

Предусматриваются специальные типы:

```
isize
usize
```

Они имеют размер указателя текущей целевой архитектуры.

Например:

```
32-bit target:
isize  = 32 bit
usize  = 32 bit

64-bit target:
isize  = 64 bit
usize  = 64 bit
```

Они предназначены для:

- размеров объектов;
- индексов памяти;
- смещений;
- адресной арифметики;
- количества элементов;
- системных API.

---
# 6. Логический тип

```
bool
```

Допустимые значения:

```
true
false
```

`bool` не обязан занимать ровно один байт в каждом внутреннем представлении VM, однако ABI-представление должно быть определено отдельно.

В стандартном memory representation рекомендуется:

```
bool = 1 byte
```

---
# 7. Типы с плавающей точкой

Предусматриваются:

```
float32
float64
```

Предполагаемое представление:

```
float32 = IEEE 754 binary32
float64 = IEEE 754 binary64
```

Требование будет окончательно закреплено при описании target ABI.

---
# 8. Символьный тип

Предусматривается:

```
char
```

`char` представляет один кодовый элемент UTF-8/байтового представления либо другой формат, если это будет определено runtime.

Для системного программирования `char` должен иметь размер:

```
1 byte
```

При этом `char` не следует автоматически трактовать как полноценный Unicode code point.

Для Unicode будет предусмотрен отдельный механизм.

---
# 9. Строки

Базовый тип:

```
string
```

Строка является объектным типом runtime.

Концептуально:

```
string
 ├── data
 ├── length
 └── metadata
```

`string` не является встроенным фиксированным массивом символов.

Это позволит runtime реализовать:

- UTF-8;
- динамический размер;
- безопасное управление памятью;
- оптимизации;
- интернирование строк.

Для низкоуровневой работы используются:

```
pointer<char>
```

или специальные byte-buffer типы.

---
# 10. Тип void

```
void
```

`void` означает отсутствие возвращаемого значения.

Пример:

```AZONE
void printHello() { 
	print("Hello"); 
}
```

`void` не является обычным значением и не может использоваться как тип переменной.

---
# 11. Null

Специальное значение:

```
null
```

может использоваться с nullable-ссылочными типами.

Пример:

```AZONE
Player player = null;
```

Однако для системного программирования требуется различать:

```
null reference
null pointer
invalid address
```

Поэтому `null` не должен автоматически означать физический адрес `0` во всех контекстах.

---
# 12. Указатели

Для низкоуровневого программирования вводится параметризованный тип:

```
pointer<T>
```

Пример:

```AZONE
pointer<uint8> buffer;
pointer<int32> value;
```


Указатель содержит адрес объекта или области памяти.

Размер указателя зависит от target architecture.

На 64-bit платформе:

```
pointer<T> = 64 bits
```

На 32-bit:

```
pointer<T> = 32 bits
````

---
# 13. Адресный тип

Предусматривается специальный тип:

```
address
```

Он предназначен для хранения числового адреса памяти.

Пример концептуального использования:

```
address addr = ...;
```

Преобразование:

```
address ↔ pointer<T>
````

должно требовать специального системного/unsafe-контекста.

---
# 14. Unsafe-код

AZONE LANG должен разделять безопасный и низкоуровневый код.

Предусматривается специальный контекст:

```
unsafe {
    ...
}
```

Внутри него могут разрешаться операции:

- разыменование указателей;
- преобразование адресов;
- ручная работа с памятью;
- volatile access;
- memory-mapped I/O;
- native-вызовы;
- другие операции, нарушающие обычные гарантии безопасности языка.

Пример:

```AZONE
unsafe { 
	pointer<uint32> reg = ...; 
	*reg = 0x01; 
}
```


Точный синтаксис разыменования будет определён позже.

---
# 15. Ссылки

Предусматривается тип:

```
reference<T>
```

Ссылка отличается от указателя.

Указатель:

```
pointer<T>
```

может представлять адрес.

Ссылка:

```
reference<T>
```

представляет валидную ссылку на объект согласно правилам системы типов.

Предполагается:

```
pointer<T>   → может быть null
reference<T> → не может быть null
```

Точные правила времени жизни будут определены в Memory Model.

---
# 16. Массивы

Предусматриваются два основных вида массивов.

## 16.1 Статический массив

```
T[N]
```

Пример:

```AZONE
int32[10] values;
```


Размер известен во время компиляции.

## 16.2 Динамический массив

Предусматривается runtime-тип:

```
array<T>
```

Пример:

```
int32[10] values;
```

Он может изменять количество элементов во время выполнения.

---
# 17. Индексация

Массивы индексируются оператором:

```
[]
```

Пример:

```AZONE
int32[10] values; 

values[0] = 100; 
values[1] = 200;
```

Индекс должен иметь целочисленный тип.

---
# 18. Кортежи

Предусматривается возможность введения tuple-типа:

```
tuple<T1, T2, ...>
```

Например:

```AZONE
tuple<int32, string> result;
```

Кортежи могут использоваться для возврата нескольких значений.

Точная синтаксическая форма будет утверждена позднее.

---
# 19. Перечисления

Предусматривается:

```
enum
```

Пример:

```AZONE
enum Color { 
	Red, 
	Green, 
	Blue 
}
```

Каждое значение enum должно иметь определённое целочисленное представление.

Тип базового представления должен иметь возможность задаваться явно.

Например:

```AZONE
enum Color : uint8 { 
	Red, 
	Green, 
	Blue 
}
```

---
# 20. Функциональные типы

Функция рассматривается как тип.

Концептуально:

```
function<ReturnType(Parameters...)>
```

Например:

```AZONE
function<int32(int32, int32)>
```

Это необходимо для:

- callback;
- событий;
- системных API;
- потоков;
- GUI;
- асинхронных механизмов;
- функциональных объектов.

---
# 21. Пользовательские типы

Пользователь сможет создавать:

```
class
interface
enum
```

В дальнейшем могут быть добавлены:

```
struct
union
```

`struct` особенно важен для системного программирования и ABI, поэтому возможность его введения должна быть сохранена.

---
# 22. Class

Класс является ссылочным объектным типом.

Пример:

```AZONE
class Player { 
	int32 health; 
	string name; 
}
```

Класс может содержать:

- поля;
- методы;
- конструкторы;
- статические члены;
- виртуальные методы;
- свойства;
- события в будущем.

---
# 23. Value types и reference types

AZONE LANG должен явно разделять:

```
Value Type
Reference Type
```

Value type содержит само значение.

Пример:

```
int32
float64
bool
```

Reference type содержит ссылку на объект.

Например:

```
class Player
```

Конкретная модель копирования и передачи параметров будет определена Memory Model.

---
# 24. Типизация выражений

Каждое выражение имеет тип.

Например:

```AZONE
int32 a = 10; 
int32 b = 20; 

int32 c = a + b;
```

Выражение:

```
a + b
```

имеет тип:

```
int32
```

---
### 25. Арифметические операции

Для числовых типов:

```
+
-
*
/
%
```

Компилятор должен проверять совместимость типов операндов.

Например:

```AZONE
int32 a = 10; 
int32 b = 20; 

int32 c = a + b;
```

разрешено.

Но:

```AZONE
string a = "Hello"; 
int32 b = 10; 

a - b;
```

должно вызвать ошибку типов.

---
# 26. Деление

Тип результата зависит от типов операндов.

Для целых типов:

```AZONE
int32 a = 10; 
int32 b = 3; 

int32 result = a / b;
```

используется целочисленное деление.

Для floating-point:

```AZONE
float64 result = 10.0 / 3.0;
```

используется вещественное деление.

---
# 27. Деление на ноль

Для целочисленного деления на ноль поведение должно быть определено отдельно.

Предварительное решение:

```
Runtime Exception
```

Для compile-time известных выражений компилятор может выдавать ошибку ещё на этапе компиляции.

---
# 28. Сравнение

Операторы:

```
==
!=
<
>
<=
>=
```

возвращают:

```
bool
```

Пример:

```AZONE
bool result = a < b;
```

---
# 29. Логические операции

```
!
&&
||
```

работают с `bool`.

Операторы `&&` и `||` используют short-circuit evaluation.

Например:

```AZONE
if (ptr != null && ptr->value > 10) { 
	... 
}
```

вторая часть не должна вычисляться, если первая часть ложна.

---
# 30. Побитовые операции

Для целочисленных типов:

```
&
|
^
~
<<
>>
```

Операции должны работать на уровне битового представления.

Это необходимо для:

- драйверов;
- системных флагов;
- регистров;
- протоколов;
- MMIO;
- системных структур данных.

---
# 31. Неявные преобразования

Неявные преобразования должны быть ограничены.

Например:

```
int8 → int16
int16 → int32
int32 → int64
```

могут быть безопасными расширениями.

Однако:

```
int64 → int8
```

не должно выполняться неявно.

Это предотвращает скрытую потерю данных.

---
# 32. Явное преобразование

Для потенциально опасных преобразований предусматривается явный cast.

Предварительный синтаксис:

```AZONE
int8 small = cast<int8>(value);
```

В дальнейшем может быть введено несколько видов преобразований:

```
cast
bitcast
reinterpret
```

Особенно `reinterpret` должен быть ограничен unsafe-контекстом.

---
# 33. Переполнение

Для целочисленных операций политика переполнения должна быть определена явно.

Предварительно:

**Debug**

Переполнение может обнаруживаться runtime-проверкой.

**Release**

Для операций, где это необходимо системному программированию, допускается wrapping arithmetic.

В дальнейшем следует предусмотреть отдельные операции:

```
checked
unchecked
saturating
wrapping
```

Это позволит системному программисту самостоятельно выбирать требуемую семантику.

---
# 34. Константные выражения

Компилятор должен уметь вычислять выражения, известные во время компиляции.

Например:

```AZONE
const int32 SIZE = 1024 * 1024;
```

Результат должен быть вычислен compiler'ом.

Это необходимо для:

- размеров массивов;
- системных констант;
- битовых масок;
- layout структур;
- оптимизации.

---
# 35. Const

`const` запрещает изменение значения после инициализации.

```AZONE
const int32 MAX_USERS = 100;
```

Попытка:

```AZONE
MAX_USERS = 200;
```

является ошибкой компиляции.

---
# 36. Readonly

Предусматривается отдельное понятие:

```
readonly
```

В отличие от `const`, `readonly` может применяться к объектным полям и ссылкам.

Пример:

```AZONE
class Device { 
	readonly int32 id; 
}
```

Это позволяет создать неизменяемые после инициализации части объекта.

---
# 37. Lvalue и Rvalue

Модель выражений должна различать:

```
lvalue
rvalue
```

Например:

```AZONE
int32 value = 10; 

value = 20;
```

`value` в левой части присваивания является lvalue.

Результат:

```
value + 10
```

является rvalue.

Это различие необходимо для:

- ссылок;
- указателей;
- move-семантики в будущем;
- операторов присваивания;
- перегрузки операторов.

---
# 38. Адрес операнда

Для получения адреса предусматривается оператор:

```
&
```

Пример:

```AZONE
int32 value = 10; 

pointer<int32> ptr = &value;
```

Разыменование:

```
*
```

Пример:

```AZONE
*ptr = 20;
```

Операции должны быть доступны в unsafe-контексте, если они не могут быть статически доказаны безопасными.

---
# 39. Доступ к полю через указатель

Предусматривается оператор:

```
->
```

Пример:

```AZONE
pointer<Player> player; 

player->health;
```

Эквивалентная концепция:

```
(*player).health
```

---
# 40. Операторы как расширяемый механизм

Операторы должны быть частью общей системы расширения языка.

Встроенный оператор:

```
+
```

концептуально может быть представлен как операция над типами.

Например:

```
int32 + int32
float64 + float64
Vector3 + Vector3
```

Таким образом, пользовательские типы смогут определять собственное поведение операторов.

---
# 41. Перегрузка операторов

Для классов должна предусматриваться возможность перегружать определённые операторы.

Например:

```AZONE
class Vector2 { 
	float64 x; 
	float64 y; 
	
	operator +(Vector2 other) { 
		... 
	} 
}
```

Точный синтаксис будет утверждён в спецификации [[Specification 0.4  |объектной модели]].

---
# 42. Перегрузка функций

AZONE LANG должен поддерживать перегрузку функций.

Например:

```AZONE
void print(int32 value) { 
	... 
}

void print(string value) { 
	... 
} 

void print(bool value) { 
	... 
}
```


Компилятор выбирает подходящую функцию на основе типов аргументов.

---
# 43. Generic-типы

Для системного и прикладного программирования необходимо предусмотреть обобщённые типы.

Предварительно:

```AZONE
class Box<T> { 
	T value; 
}
```

Использование:

```AZONE
Box<int32> number; 
Box<string> text;
```

Generic-система будет разработана отдельной спецификацией.

---
# 44. ABI и системное программирование

AZONE LANG должен иметь формально определённый ABI.

ABI должен описывать:

- размеры типов;
- выравнивание;
- layout объектов;
- layout структур;
- передачу аргументов;
- возвращение значений;
- calling convention;
- представление указателей;
- представление boolean;
- представление enum;
- layout массивов;
- взаимодействие с native-функциями.

Это является обязательным требованием для будущей ОС.

---
# 45. Native ABI

AZONE должен уметь вызывать функции внешнего ABI.

Например:

```AZONE
extern native int32 system_call(int32 id);
```

Точный синтаксис будет определён в спецификации Native API.

Необходимо предусмотреть как минимум возможность взаимодействия с:

```
C ABI
```

поскольку Linux kernel и значительная часть системного окружения используют C ABI.

---
# 46. Freestanding Runtime

AZONE LANG должен поддерживать режим, в котором программа может работать без полноценной стандартной библиотеки.

Например:

```
AZONE Freestanding
```

В этом режиме программа получает минимальный runtime:

```
Memory
Types
Exceptions/Errors
Native Calls
Basic VM Services
```

Это необходимо для:

- ранней загрузки ОС;
- системных компонентов;
- низкоуровневых сервисов;
- специальных runtime-компонентов;
- аппаратного взаимодействия.

---
# 47. Hosted Runtime

Обычные приложения будут использовать полноценный runtime:

```
AZONE Hosted Runtime
```

Он может предоставлять:

```
String
Array
File
Network
Thread
Process
GUI
IPC
Time
Collections
Reflection
```

Таким образом:

```
Freestanding
    │
    └── минимальный runtime

Hosted
    │
    └── полноценный runtime
```

---
# 48. Runtime для собственной ОС

Архитектура должна предусматривать:

```
AZONE Runtime
       │
       ├── Core
       ├── Memory
       ├── Objects
       ├── Threads
       ├── IPC
       ├── Process
       ├── File System
       ├── Graphics
       └── Device API
```

Однако эти компоненты не являются частью языка.

Они относятся к платформе AZONE OS.

Таким образом:

```
AZONE LANG
    ≠
AZONE OS
```

Язык должен оставаться переносимым.

---
# 49. Целевые архитектуры CPU

Первоначальная целевая архитектура:

```
x86-64
```

Это соответствует современной 64-bit Linux-среде и позволяет сначала реализовать ABI для одной архитектуры.

Архитектура языка при этом не должна зависеть от x86-64.

В дальнейшем:

```
x86-64
ARM64
RISC-V 64
```

могут стать отдельными targets.

---
# 50. Target-модель

Компилятор должен принимать target:

```
azc --target=x86_64 ...
```

В будущем:

```
azc --target=aarch64 ...
azc --target=riscv64 ...
```

Target должен определять:

- ABI;
- размер указателя;
- alignment;
- calling convention;
- native types;
- machine backend.

---
# 51. Главное архитектурное правило

AZONE LANG не должен считать VM единственным способом существования программы.

Должны существовать как минимум две концепции:

```
AZONE Bytecode 
	│ 
	▼ 
AZONE VM
```

и:

```
AZONE IR 
	│ 
	▼ 
Native Backend 
	│ 
	▼ 
Machine Code
```

На ранних этапах второй путь может отсутствовать.

Но архитектура компилятора должна быть спроектирована так, чтобы его можно было добавить без переписывания языка.
